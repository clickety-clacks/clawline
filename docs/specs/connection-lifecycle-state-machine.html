T100 Connection Lifecycle State Machine Redesign

Clawline iOS shared spec. Prepared 2026-05-27. Canonical artifact: /Users/mike/shared-workspace/clawline/specs/connection-lifecycle-state-machine.html.

Decision: Clawline iOS must replace distributed connection lifecycle decisions with one explicit lifecycle state machine authority.

The lifecycle authority owns phase transitions, reconnect admission, replay completion, and stale-attempt rejection. ChatViewModel, ProviderChatService, and URLSessionWebSocketConnector may emit events or intents into that authority, but they may not independently decide lifecycle phase.

Source Basis

  • Tracker T100 goal: replace the distributed, implicit connection lifecycle across ChatViewModel, ProviderChatService, and URLSessionWebSocketConnector with a single explicit state machine covering idle, connecting, authenticating, replaying, live, recovering, and failed, with a single authority and explicit replay-complete barrier.
  • Preserved source material: /Users/mike/shared-workspace/clawline/implementation_details/connection-lifecycle.md. This spec carries forward only the details that define product-visible lifecycle behavior or prevent the known reconnect/replay failure modes.

Goal

T100-GOAL-01 Make Clawline iOS connection status and message replay behavior deterministic by routing all connection lifecycle transitions through one explicit state machine.

T100-GOAL-02 Prevent reconnect loops, stale replay cursors, and late cache restores from moving the app backward after a newer connection attempt has succeeded.

Non-Goals

  • T100-NG-01 This spec does not redesign message rendering, transcript layout, typing indicators, notifications, or send-button visuals.
  • T100-NG-02 This spec does not define provider-side protocol changes.
  • T100-NG-03 This spec does not require a specific Swift type name, file layout, actor implementation, or migration sequence beyond the behavioral ownership rules below.
  • T100-NG-04 This spec does not add new legacy compatibility paths or alternate reconnect mechanisms.

Lifecycle Model

ID Phase Meaning Allowed Exit
T100-PH-01 idle No active provider connection attempt is running. connecting when a connection is requested.
T100-PH-02 connecting The transport is being opened. authenticating on transport open; recovering or failed on failure according to retry policy.
T100-PH-03 authenticating The opened transport is proving it is accepted for the current Clawline session. replaying on authentication success; recovering or failed on rejection/failure according to retry policy.
T100-PH-04 replaying The app is catching up server-sourced messages from the connection snapshot cursors. live only after the replay-complete barrier passes; recovering or failed on failure according to retry policy.
T100-PH-05 live The connection is current, replay has completed, and live events may be applied. recovering on transport interruption or explicit lifecycle recovery event; idle on intentional teardown.
T100-PH-06 recovering The connection has failed but remains eligible for retry. connecting when the lifecycle authority admits a retry; failed when retry policy is exhausted; idle on intentional teardown.
T100-PH-07 failed The connection is not live and automatic recovery has stopped. connecting only from an explicit user or app retry intent accepted by the lifecycle authority.

Requirements

ID Requirement Acceptance Check
T100-REQ-01 There is exactly one connection lifecycle authority for iOS phase transitions. A code search shows only the lifecycle authority writes the public connection phase. ChatViewModel, ProviderChatService, and URLSessionWebSocketConnector send events or intents to the authority instead of assigning phase directly.
T100-REQ-02 The lifecycle authority exposes only the seven phases listed in T100-PH-01 through T100-PH-07. Tests or compile-time checks fail if an implementation adds a product-visible lifecycle phase not listed in this spec.
T100-REQ-03 Each connection attempt has an epoch token, and async callbacks from stale epochs are ignored. A stale transport, auth, replay, cache, or retry callback from an older epoch cannot change phase, cursor state, or live message state after a newer epoch is active.
T100-REQ-04 replaying cannot transition to live until replay completion has been explicitly observed for the active epoch. An auth success without replay completion leaves the lifecycle out of live; a replay completion from a stale epoch is ignored.
T100-REQ-05 Reconnect intents received while the lifecycle is connecting, authenticating, replaying, or live are ignored, not queued. A late reconnect trigger during any active phase does not create a pending reconnect and does not run after the current attempt reaches live.
T100-REQ-06 While in recovering, the lifecycle authority's backoff timer is the only automatic reconnect mechanism. Transport interruption, scene activation, and other external reconnect intents during recovering do not start parallel reconnect attempts.
T100-REQ-07 Manual retry during recovering cancels the pending backoff timer, transitions immediately to connecting, resets that attempt's delay to 1 second, and does not increment the automatic recovering-attempt counter. A test drives recovering, fires manual retry, and verifies immediate retry plus unchanged automatic attempt count.
T100-REQ-08 The connection snapshot used for replay includes cursors for every known stream/session, not only the active chat session. After reconnect, inactive streams with known cursors do not replay from scratch solely because another stream was active at connection time.
T100-REQ-09 Cache restore is gap-fill input only and cannot overwrite newer server-sourced state for the active or newer epoch. A delayed cache restore arriving after live server messages does not clear, reorder, or roll back those live messages or their cursors.
T100-REQ-10 Session message and cursor mutation happens through one store mutation boundary that enforces epoch and gap-fill rules. A code search shows no direct writes to session messages or last-server-message cursors outside the chosen mutation boundary and its tests.
T100-REQ-11 Intentional teardown is distinct from recovery. An intentional user/app teardown transitions to idle and does not schedule backoff recovery.
T100-REQ-12 Only the lifecycle authority decides whether a failure moves to recovering or failed. Transport and service layers report failure facts; they do not independently mark the app recovered, failed, or live.

State Transition Checks

ID Scenario Expected Result
T100-AC-01 Fresh launch requests provider connection. idle -> connecting -> authenticating -> replaying -> live occurs in order for one epoch.
T100-AC-02 Transport opens, then a stale previous attempt emits auth or replay output. The stale output is ignored and the active epoch continues unchanged.
T100-AC-03 Replay has not completed for the active epoch. The lifecycle does not enter live.
T100-AC-04 Connection fails during connecting, authenticating, replaying, or live while retry remains available. The lifecycle enters recovering and uses one backoff path.
T100-AC-05 Multiple reconnect triggers fire during recovering. Only the admitted retry path runs; no parallel reconnect loop is created.
T100-AC-06 Manual retry is tapped during recovering. Pending backoff is cancelled and the lifecycle immediately enters connecting without increasing the automatic recovering-attempt counter.
T100-AC-07 A delayed cache restore arrives after server replay/live events. Cache fills missing gaps only and does not overwrite newer server messages or cursors.
T100-AC-08 Reconnect occurs while multiple sessions have known cursors. The replay snapshot includes all known per-session cursors, and inactive sessions do not unnecessarily replay from scratch.

Implementation Handoff

  • T100-HO-01 Implementation must stay inside Clawline iOS connection lifecycle and store/cursor mutation boundaries needed by this spec.
  • T100-HO-02 Implementation should treat existing reconnect schedulers, cache restore, transport callbacks, scene activation, and provider service events as inputs to the lifecycle authority, not as peer state machines.
  • T100-HO-03 Tests should cover transition order, stale epoch rejection, replay barrier behavior, recovering backoff admission, manual retry behavior, all-session cursor snapshots, and delayed cache restore.
  • T100-HO-04 If implementation discovers an additional product-visible phase or reconnect path is necessary, return T100 to spec work instead of adding it silently.

Open Questions
