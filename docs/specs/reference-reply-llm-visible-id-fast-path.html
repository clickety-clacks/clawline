Clawline Reference/Reply LLM-Visible ID Fast Path

This document captures the current reference/reply failure and Flynn's product fix. The core change is simple: every rendered message needs to carry the same id the LLM-side transcript can recognize, and replies should pass that id through as lightweight context instead of forcing provider-side transcript resolution.

Decision Use LLM-visible ids
Hot Path No transcript scan
Old Messages Reply button stays

Situation

On May 26, 2026, Flynn sent a Clawline prompt with a reference/reply attached. The prompt appeared to hang before becoming an agent/model turn. Gateway health was fine, OpenClaw had no running or queued tasks, and the latest user message was not persisted in the Clawline database.

The log path showed the inbound message entering the Clawline preprocessing stage named resolve_references and not reaching the later stages that persist, acknowledge, and dispatch the message.

What worked

  • Gateway HTTP and version endpoints were live.
  • The message reached Clawline inbound processing.
  • The UI knew which bubble Flynn was replying to.

What failed

  • The message did not persist before reference resolution.
  • The provider attempted expensive reference lookup on the send path.
  • The LLM never received the prompt, so the reply context never mattered.

Observed Failure Shape

The current resolver tries to turn a client-side reference into provider-readable context before the user message is acknowledged. When direct lookup fails, it can fall back to loading/scanning the referenced session transcript and Clawline event rows. In the observed stream, that meant thousands of rows and several megabytes of payload on the synchronous inbound path.

That architecture is backwards for this product need. Reply/reference is not a provider-owned lookup problem; it is a context pointer problem. The client already has the selected bubble. The missing bridge is the id that the LLM-visible transcript can recognize.

Product Truth

For Clawline reply/reference, success means the model sees enough structured context to understand that Flynn is replying to a prior message. It does not require the provider to prove the referenced message exists before accepting the send.

If the id is stale, invalid, or not present in the model's active context, the model can say it does not know what Flynn is referring to. That is a better product failure than blocking the send, scanning the transcript, or silently dropping the turn before it reaches the model.

Required Fix

RR-01
Every message delivered to a Clawline client must include an LLM-visible message id: the canonical id that the provider/model-side transcript will recognize when it appears in prompt context.
RR-02
The client must store that id on the rendered/local message model and use it when building reply/reference payloads. The local UI id, replay id, compact id, or temporary optimistic id is not enough for model-visible reply grounding.
RR-03
When Flynn replies to a message, the client sends lightweight structured metadata containing the LLM-visible id, optional role, and a bounded visible preview. The payload should identify the referenced message; it should not paste the whole referenced text into the composer.
RR-04
The provider/server must not semantically validate, hydrate, or resolve that id on the inbound hot path. It may enforce cheap shape and size limits, then persist/ack the user message normally and pass the metadata through to model context.
RR-05
No session-wide transcript scan, transcript-file read, or full event-row scan is allowed before message persistence/acknowledgement for reply/reference handling.
RR-06
The LLM context should explicitly expose the pointer, for example: user is replying to message <llmVisibleMessageId>, plus optional role/preview. The model decides whether that id is meaningful in its context.
RR-07
If a message does not have an LLM-visible id, the Reply button still appears in the UI. Activating it opens a dialog telling the user to update to the newest Clawline fork; it must not silently disappear or attempt the old slow resolver path.
RR-08
The missing-id dialog text should be direct: Please update to the newest Clawline fork to reply to this message.

Suggested Payload Shape

{
  "references": [
    {
      "kind": "reply",
      "llmVisibleMessageId": "s_...",
      "role": "assistant",
      "preview": "Bounded visible snippet from the bubble"
    }
  ]
}

The exact field name can match the existing codebase if another canonical name already exists, but the invariant is fixed: the id sent back by the client must be the one the LLM-visible transcript can recognize.

What Not To Build

  • Do not repair this by making provider-side fallback scanning faster.
  • Do not block send while trying to prove the referenced message exists.
  • Do not hide the Reply button for older messages that lack the new id.
  • Do not treat a UI token or sent-bubble indicator as proof unless the LLM-visible id reaches model context.

Acceptance Checks

AC-01
A freshly loaded message bubble contains the LLM-visible id in client state and can send it back in a reply/reference payload.
AC-02
A reply/reference send persists and acknowledges before any expensive reference enrichment work can run.
AC-03
Provider logs for a reply/reference send show no full-session reference scan before persistence/acknowledgement.
AC-04
The model-visible prompt context contains the referenced LLM-visible id and bounded metadata.
AC-05
For an old/no-id message, the Reply button remains present and opens the update dialog instead of sending a broken reference or hiding the affordance.
