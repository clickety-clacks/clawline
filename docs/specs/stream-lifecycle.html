Stream Lifecycle Spec (Server-Side)

Status: Approved for implementation

Last updated: 2026-05-30 (Spec Review closed; original spec date 2026-02-24)

Related: clickety-clacks/clawline#116, #115

Depends on: specs/multi-stream.md, provider-architecture.md, specs/clawline-invariants.md

Phase note:

  • Phase A = existing multi-stream CRUD baseline in `multi-stream.md`.
  • Phase B = fork/merge behavior defined in this spec.

    • 1. Goal

    Enable CLU to manage stream lifecycle from the server side for a user without requiring the iOS client bearer token, covering:

  • Create/rename/delete stream via provider API.
  • Auth for server-side stream management.
  • Fork stream flow (Phase B): branch a conversation into a new stream with carried context.
  • Merge stream flow (Phase B): converge two streams after a topic resolves.

    • 2. Non-Goals

  • Replacing existing client-side `/api/streams` user-auth endpoints.
  • Redesigning session key format (session keys remain canonical IDs).
  • UI specification for iOS fork/merge controls.
  • Full CRDT/three-way semantic merge of message history.
  • Automatic background stream deletion/cleanup.

    • 3. Current State Summary

  • `channel-create`, `channel-edit`, and `channel-delete` exist in provider `actions.ts`.
  • Those actions call `callStreamApi()` with bearer auth available only to the iOS app.
  • CLU can read stream rows from SQLite (`stream_sessions`) but cannot mutate streams.

    • 4. Invariants (Binding)

  • Session keys remain the only stream routing identifiers.
  • Built-in stream protections from Phase A remain in force.
  • Stream lifecycle mutations are explicit API actions; no autonomous expiry/deletion jobs are introduced.
  • Fork and merge emit explicit stream-topology events, same as create/rename/delete.

    • 5. Auth Model (Recommended)

    5.1 Model

    Use a single provider-side secret header for server-side calls:

  • Header: `X-CLU-Secret: <secret>`
  • Secret config key: `clawline.server.cluSecret`
  • Secret source: provider config/runtime env only (never sent to iOS client)

    • This secret allows CLU to bypass the iOS bearer-token requirement for server lifecycle endpoints.

    5.2 Secret requirements

  • Minimum entropy: 128 bits.
  • Minimum length: 22 chars base64url (or equivalent entropy string).
  • Secret must not be checked into source control.
  • Rotation: provider supports rotation via restart or config reload.

    • 5.3 Validation rules

  • Missing/invalid `X-CLU-Secret` returns `403 clu_secret_invalid`.
  • Valid secret proceeds to normal stream guardrails (built-in protection, last-stream protection, etc.).
  • Every endpoint path includes `:userId`; provider must reject unknown user with `404 user_not_found`.

    • 5.4 Transport expectation

  • Default deployment is local/private network per provider architecture.
  • TLS termination remains operator-managed and out of scope for this spec.

    • 6. API Surface (Provider)

    All endpoints below are provider endpoints and require X-CLU-Secret.

    6.1 Create stream

    POST /api/server/users/:userId/streams

    Request:

    
{
  "displayName": "Loupe",
  "idempotencyKey": "req_123"
}

    Response 201: stream payload matches Phase A stream schema.

    Errors:

  • `404 user_not_found`
  • `400 invalid_display_name`
  • `409 stream_limit_reached`

    • 6.2 Rename stream

    PATCH /api/server/users/:userId/streams/:sessionKey

    Request:

    
{
  "displayName": "Deploy Log"
}

    Response 200: updated stream payload.

    Errors:

  • `404 user_not_found`
  • `404 stream_not_found`
  • `409 built_in_stream_rename_forbidden`

    • 6.3 Delete stream

    DELETE /api/server/users/:userId/streams/:sessionKey

    Header:

  • `X-Idempotency-Key: req_456`

    • Response 200:

    
{
  "deletedSessionKey": "agent:main:clawline:flynn:s_8fa12c44"
}

    Errors:

  • `404 user_not_found`
  • `404 stream_not_found`
  • `409 built_in_stream_delete_forbidden`
  • `409 last_stream_delete_forbidden`

    • 6.4 Idempotency contract

    Applies to create/delete/fork/merge.

  • Scope key by `(userId, endpoint, idempotencyKey)`.
  • First successful request stores canonical response JSON.
  • Exact replay returns stored response with original status.
  • Same key with different normalized request body returns `409 idempotency_key_reused`.
  • Retention: 7 days (reuse existing `stream_idempotency` table and cleanup policy).

    • 7. Fork (Phase B)

    7.1 Endpoint

    POST /api/server/users/:userId/streams/:sessionKey/fork

    Request:

    
{
  "displayName": "Parser Refactor",
  "seed": {
    "summary": "This branch tracks parser refactor decisions and follow-up tasks.",
    "sourceMessageIds": ["s_101", "s_102", "s_109"],
    "quotedSnippets": [
      {
        "messageId": "s_102",
        "text": "This conversation deserves its own stream."
      }
    ]
  },
  "idempotencyKey": "req_789"
}

    Response 201:

    
{
  "forkedFrom": "agent:main:clawline:flynn:main",
  "stream": {
    "sessionKey": "agent:main:clawline:flynn:s_a1b2c3d4",
    "displayName": "Parser Refactor",
    "kind": "custom",
    "orderIndex": 5,
    "isBuiltIn": false,
    "createdAt": 1771905600000,
    "updatedAt": 1771905600000
  },
  "seedMessageId": "s_5001"
}

    Errors:

  • `404 user_not_found`
  • `404 stream_not_found`
  • `422 fork_source_message_not_found`
  • `422 fork_quote_message_mismatch`
  • `422 fork_seed_too_large`

    • 7.2 Fork semantics

  • Provider creates child stream and appends at end (`orderIndex = max + 1`).
  • Provider validates every `sourceMessageId` exists in parent stream.
  • Provider validates every `quotedSnippets[].messageId` is present in `sourceMessageIds`.
  • Provider enforces bounded fork seed payloads: `summary` max 2,000 chars, `sourceMessageIds` max 20, `quotedSnippets` max 5, and each quoted snippet `text` max 500 chars.
  • Provider writes one seed message to child stream containing summary and references.
  • Provider writes one parent note: `Forked to <displayName>` with child `sessionKey`.
  • No historical message copy.
  • Provider emits:
  • `stream_created`
  • `stream_forked` with `{ parentSessionKey, childSessionKey, seedMessageId }`

    • 8. Merge (Phase B)

    8.1 Endpoint

    POST /api/server/users/:userId/streams/merge

    Request:

    
{
  "sourceSessionKey": "agent:main:clawline:flynn:s_a1b2c3d4",
  "targetSessionKey": "agent:main:clawline:flynn:main",
  "summary": "Parser refactor complete. Decision: keep incremental tokenizer path.",
  "closeSource": true,
  "idempotencyKey": "req_999"
}

    Response 200:

    
{
  "merged": true,
  "mergeMessageId": "s_6001",
  "sourceSessionKey": "agent:main:clawline:flynn:s_a1b2c3d4",
  "targetSessionKey": "agent:main:clawline:flynn:main",
  "sourceClosed": true
}

    Errors:

  • `404 user_not_found`
  • `404 stream_not_found`
  • `422 merge_source_target_same`
  • `409 built_in_stream_close_forbidden`

    • 8.2 Merge semantics

  • Provider writes one merge summary message into target stream.
  • Provider always writes one source-stream note that references target stream.
  • If `closeSource=true`, provider marks source stream `status=closed` (read-only); merge does not hard-delete source.
  • Phase B does not add a reopen endpoint. Reopening closed merged streams is deferred until a product need exists; users can still explicitly delete permitted closed custom streams.
  • Built-in streams may be merge targets.
  • Built-in streams may not be closed by merge (`closeSource=true` forbidden when source is built-in).
  • Provider emits:
  • `stream_merged` with `{ sourceSessionKey, targetSessionKey, mergeMessageId, sourceClosed }`
  • `stream_updated` if source stream status changes.

    • 9. Data Model Additions (Provider DB)

    9.1 `stream_sessions` additive fields

  • `createdBy TEXT NOT NULL DEFAULT 'user'` (`user | clu`)
  • `status TEXT NOT NULL DEFAULT 'active'` (`active | closed`)

    • Migration note:

  • Existing rows remain `createdBy='user'` by default (historical iOS-created/custom streams).

    • closed semantics:

  • Closed streams remain visible in `GET /api/streams` and WS snapshots.
  • Closed streams are read-only for new message sends.
  • Closed streams are still deletable through explicit delete endpoint (unless built-in protections apply).

    • 9.2 New table `stream_lineage`

    
CREATE TABLE IF NOT EXISTS stream_lineage (
  userId TEXT NOT NULL,
  relationId TEXT NOT NULL,
  relationType TEXT NOT NULL,    -- fork | merge
  sourceSessionKey TEXT NOT NULL,
  targetSessionKey TEXT NOT NULL,
  contextJson TEXT,
  createdAt INTEGER NOT NULL,
  PRIMARY KEY (userId, relationId)
);

    Persistence rule:

  • Lineage writes are idempotent with request idempotency (same replay must not duplicate row or fail).

    • Purpose:

  • Track fork/merge lineage.
  • Support future parent/child and merge navigation.

    • 10. WebSocket Event Additions

    New S2C events:

  • `stream_forked`
  • `stream_merged`

    • Payloads:

    
{
  "type": "stream_forked",
  "parentSessionKey": "agent:main:clawline:flynn:main",
  "childSessionKey": "agent:main:clawline:flynn:s_a1b2c3d4",
  "seedMessageId": "s_5001"
}

    
{
  "type": "stream_merged",
  "sourceSessionKey": "agent:main:clawline:flynn:s_a1b2c3d4",
  "targetSessionKey": "agent:main:clawline:flynn:main",
  "mergeMessageId": "s_6001",
  "sourceClosed": true
}

    Delivery rule:

  • Broadcast to all active authenticated sockets for that `userId`.
  • Offline clients reconcile via normal reconnect snapshot/replay path.

    • 11. OpenClaw Core vs Clawline Provider Boundary

    11.1 Decision

    This is 100% Clawline provider work for #116.

    No OpenClaw core changes are required.

    11.2 Why no core change is needed

  • Stream lifecycle behavior is Clawline-domain logic already implemented in provider stream actions.
  • `X-CLU-Secret` validation is provider-specific endpoint policy, not shared core protocol behavior.
  • Fork/merge semantics are Clawline stream-topology features within provider storage/events.

    • 11.3 What would force a core change later

    Core change is only needed if one of these becomes a requirement:

  • A provider-agnostic server-auth mechanism shared by multiple plugins/providers.
  • Core-level authorization middleware that must own secret validation.
  • Core protocol additions that all clients/providers must understand.

    • None of these are required for this issue.

    12. Security and Guardrails

  • `X-CLU-Secret` must be configured out-of-band and not exposed to clients.
  • Provider logs all server-side lifecycle mutations with `actor=clu`.
  • Rate limits (keyed by `userId` path parameter):
  • create: 20/min/user
  • rename: 30/min/user
  • delete: 10/min/user
  • fork: 10/min/user
  • merge: 10/min/user
  • All mutating endpoints require idempotency keys.

    • 13. Acceptance Checks

  • CLU can create, rename, delete custom streams via provider server-side API using `X-CLU-Secret` only.
  • Invalid/missing secret is rejected with `403 clu_secret_invalid`.
  • Unknown `userId` is rejected with `404 user_not_found`.
  • Built-in and last-stream protections still apply to server-side calls.
  • Fork validates source references, creates child stream, writes child seed context, and parent reference note.
  • Merge validates source/target constraints, writes target summary, writes source note, and optionally closes source.
  • WS broadcasts lifecycle changes to all authenticated user clients and reconnect path reconciles state.
  • Idempotency replay returns original result for create/delete/fork/merge.
  • Implementation lands fully in Clawline provider; no OpenClaw core changes.

    • 14. Implementation Handoff

  • Add provider endpoints near existing `/api/streams` handlers and route through shared stream mutation code paths.
  • Add provider config key `clawline.server.cluSecret` with validation on startup.
  • Add tests for secret validation (`403`), unknown user (`404`), idempotency replay, fork/merge validation, and closed-stream behavior.
  • Keep `sessionKey` as canonical key in all payloads, routes, and DB records.

    • 15. Spec Review Decisions

  • SRD1: Source-stream reopen after merge is deferred out of Phase B. Closed merged streams stay visible/read-only and remain explicitly deletable where normal delete guardrails allow it.
  • SRD2: Fork seed payloads have explicit limits: summary 2,000 chars, 20 source message IDs, 5 quoted snippets, 500 chars per quoted snippet.
