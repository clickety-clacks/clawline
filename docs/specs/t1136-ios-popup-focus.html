T1136 iOS Chat Popup Focus

Focused Clawline technical specification for T1136. Prepared 2026-05-24.

Decision: on iOS/iPadOS, opening the chat stream popup while the software keyboard is already visible transfers text focus from the prompt composer to the popup filter. Closing that popup while the software keyboard is still visible restores focus to the prompt composer only when the popup focus handoff actually displaced composer focus.

Requirements

ID Requirement
R1136-01 On iOS/iPadOS, if the chat stream popup opens while the software keyboard is already visible, the popup filter input receives text focus.
R1136-02 When the popup closes while the software keyboard is still visible, focus returns to the prompt composer only if T1136's popup-opening focus handoff displaced the composer for that popup presentation.
R1136-03 Opening the popup when the software keyboard is not visible must not summon the software keyboard solely for the popup filter.
R1136-04 If the popup closes after the software keyboard has been dismissed, T1136 must not restore composer focus or re-open the software keyboard.
R1136-05 The software-keyboard focus behavior applies whether the popup is opened by touch on the stream dots or through an existing keyboard command path.
R1136-06 Existing popup filtering, highlighted-row synchronization, arrow-key navigation, Return activation, clear-filter behavior, inline rename focus, track-picker behavior, and stream selection behavior remain unchanged except for the specified focus handoff.
R1136-07 Normal prompt behavior when the popup is not open remains unchanged, including typing, submit, attachment picker focus restoration, mention picker behavior, and prompt focus shortcuts.
R1136-08 Hardware keyboard behavior is preserved. T1136 must not add new hardware shortcuts, remove existing popup focus from keyboard-open paths, or change keyboard router precedence unless required only to keep existing behavior working after the software-keyboard handoff.

Named Edge Cases

  • EC1136-01: Opening popup without software keyboard visible leaves popup filter unfocused and does not present the keyboard.
  • EC1136-02: Closing popup after keyboard dismissal leaves the composer unfocused and does not re-present the keyboard.
  • EC1136-03: Popup opened by touch while the software keyboard is up focuses the filter, matching the keyboard-open path.
  • EC1136-04: Popup opened by keyboard path preserves existing hardware-keyboard filter/navigation behavior; if software keyboard is also up, the filter is focused by the T1136 rule.
  • EC1136-05: While the filter is focused and filtering text changes the list, focus remains in the filter; selection synchronization and Return activation continue to work.
  • EC1136-06: Restoration to the composer occurs only when the popup presentation took focus from the composer because the software keyboard was already up, and only while the software keyboard remains up at close time.

Implementation Handoff

  • Scope implementation to the native iOS/iPadOS chat popup focus path. Do not add provider, web, demo, harness, or unrelated popup behavior.
  • The likely ownership boundary is ChatView: detect software keyboard visibility at popup open, request popup search focus for that presentation, remember whether composer focus should be restored, and clear that restoration flag on close or dismissal paths.
  • StreamManagerSheet should continue consuming explicit search focus request IDs and should not infer product behavior from its own appearance alone.
  • Do not move stable composer focus state into MessageInputBar; source comments identify that as fragile because the input bar is recreated during geometry changes.
  • Open questions: none from product truth. Exact implementation blocker: the Tracker context helper referenced by local process instructions is absent from this checkout.
