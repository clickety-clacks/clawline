T1153 Notification Update Date Separators

Self-contained Clawline product and technical specification for visually separating newly appended notification content inside an existing notification bubble. Prepared 2026-05-27 for T1153.

Decision: when Clawline appends new content to an already-visible notification for the same source conversation, the notification must insert a horizontal separator with a human-readable date/time label between the older content and the appended content.

The separator is a readability seam inside one existing notification card. It must preserve the current notification controls, layout hierarchy, and interaction model while making the update moment obvious on the real notification surface.

Goals

  • Make appended content inside an existing notification visually distinct from earlier content.
  • Show a human-readable time marker at the boundary where the new content begins.
  • Preserve the notification's existing controls, stack behavior, and overall card layout.
  • Keep the change local to appended notification rendering rather than introducing a new notification type.

Non-Goals

  • No redesign of notification actions, docking, peeking, reply controls, or stack placement.
  • No new notification history view, inbox, badge, or expanded transcript mode.
  • No requirement here to restyle normal single-message notifications that do not append content.
  • No implementation, deployment, or merge procedure is defined by this spec.

Terminology

TermMeaning
Notification cardThe existing Clawline notification surface for one conversation/source stream.
Existing contentThe message content already visible in that notification before an update arrives.
Appended contentNewly added message content merged into the same notification card instead of creating a new separate card.
Date separatorA horizontal divider row with a human-readable date/time label that marks the boundary between existing content and appended content.
Human-readable date/timeA user-facing label such as 12:31 PM, Today 12:31 PM, or Wed 12:31 PM that can be read directly without raw timestamps.

Product Requirements

IDRequirement
R1When new content is appended to an existing notification card, Clawline must insert exactly one date separator between the older visible content and the first appended item from that update.
R2The separator must include a horizontal visual rule plus a human-readable date/time label that indicates when the appended block began.
R3The date/time label must be derived from the appended content's timestamp boundary, not from arbitrary render time if a message timestamp exists.
R4The separator must remain visually subordinate to the message content: readable and obvious, but not louder than sender/content/action controls.
R5Existing notification controls and layout must remain intact. The separator must not displace, remove, or restyle the current control row in a way that changes product behavior.
R6If multiple new messages are appended in one update burst, they share one separator at the start of the appended block rather than receiving one separator per message.
R7If a notification is initially created with fresh content rather than appended into an existing card, no extra separator is inserted at the top solely because the notification exists.
R8Repeated append cycles to the same notification card must create a new separator for each distinct appended block so the user can see each update boundary in order.
R9The separator treatment must work on the real Clawline notification surface in the product's supported light and dark appearances.

Rendering and Interaction Notes

  • The separator belongs inside the message-content column of the existing notification card, not outside the card chrome.
  • The horizontal rule may be full-width within the content column or visually centered around the label, but it must clearly read as a boundary line.
  • The label text should stay concise. The exact formatting can follow existing Clawline timestamp conventions as long as it is human-readable and visually distinct from message body text.
  • The separator is informational only. This spec does not require tap behavior, hover behavior, or a menu.
  • If the appended block is collapsed, truncated, or otherwise constrained by existing notification behavior, the separator must still remain visible at the block boundary.

Acceptance Criteria

IDAcceptance check
A1Given an existing notification card with visible prior content, when a new message is appended into that same card, the card shows a separator row before the new message block.
A2The separator row contains both a visible horizontal divider treatment and a readable date/time label.
A3The notification's existing action/control layout still matches current product behavior after the separator appears.
A4A burst that appends multiple messages at once produces one separator for that burst, not one per appended message.
A5A second later append to the same card creates another separator at the next boundary, preserving the earlier separator.
A6A newly created notification without prior content does not show an unnecessary leading separator.
A7Real notification-surface proof in both the active product appearance and content layout shows the separator is readable and not visually breaking the card.
