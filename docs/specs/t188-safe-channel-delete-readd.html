T188 — Clawline: Implement safe channel delete + re-add flow, then re-enable deleteAccount

Status target: Spec Review candidate · Artifact path: /Users/mike/shared-workspace/clawline/specs/t188-safe-channel-delete-readd.html

Spec ticket: T188 Product area: Clawline provider Scope: remove → re-add safety Implementation: not started

TL;DR

Clawline channel deletion cannot be re-enabled until removing the channel performs a controlled gateway shutdown, and re-adding the channel performs a coordinated config write plus fresh server.cluSecret activation so CLU and the running gateway never disagree about auth state.

This spec sets the product contract to: delete stops the gateway before config removal; re-add writes a new secret and brings the gateway back only with that new secret active; deleteAccount remains suppressed until the full round-trip is proven end-to-end.

Product truth and problem statement

T188 exists because Clawline config is not just a disposable account credential. It contains gateway operating state, including server.cluSecret, network settings, media paths, and other runtime-relevant fields. A naive delete would remove the on-disk config while the gateway keeps running with stale in-memory state, breaking CLU authentication and leaving the system in a deceptive half-alive state.

The feature is therefore not “allow account deletion.” The feature is “make Clawline delete/re-add a safe lifecycle transition for the gateway product.”

Proposed product contract

  • Remove with delete is a destructive lifecycle action, not a cosmetic config change.
  • Remove without delete may disable the channel, but must not pretend to validate safe re-onboarding.
  • Re-add must either start a stopped gateway with the freshly written secret or perform a controlled restart that guarantees the new secret is live before the gateway is considered healthy again.
  • Until hot-reload proof exists, restart is the required truth path for secret rotation. This is a product safety decision, not an inference that hot reload is impossible.

Requirements

R1 — Destructive remove must stop the live Clawline gateway before config deletion

If the user performs openclaw channels remove clawline --delete or any equivalent UI delete action, the system must first drive the active Clawline gateway into a stopped state before deleting the Clawline account/config surface.

R2 — No broken half-state may be presented as success

The operation must fail closed if the gateway cannot be confirmed stopped. Deleting config while the gateway remains live is forbidden. User-visible success must mean the gateway is stopped and the deleted config is no longer authoritative.

R3 — Delete must clean up gateway-owned Clawline runtime state

The shutdown path must give Clawline a chance to clean up its own runtime-owned state on shutdown. This includes the same shutdown semantics the gateway would normally execute for a controlled stop; silent orphaning is not acceptable product behavior.

R4 — Re-add must create a fresh CLU secret

Any re-add / re-onboard flow after destructive removal must generate a new channels.clawline.server.cluSecret. Reusing a removed secret is forbidden.

R5 — Re-add must make the new secret live before reporting readiness

After writing the new config, the running gateway must authenticate CLU requests with the new secret and reject the old secret before the setup flow reports completion.

R6 — Secret rotation truth is restart-until-proven-otherwise

Because T188’s source truth explicitly identifies in-memory/out-of-disk secret skew as the failure mode, the required safe baseline is a controlled gateway restart as part of re-add unless an explicit hot-reload seam is implemented and proven equivalent. Review cannot assume existing config reload behavior is sufficient.

R7 — Re-add must preserve non-secret user intent where safe

The re-add flow may restore defaultable fields such as port/bind defaults, but it must not silently discard recoverable Clawline user intent without telling the user. The implementation must define which fields are regenerated, preserved, or re-prompted.

R8 — Delete UX must communicate gateway impact before execution

The destructive delete affordance must warn that it will stop Clawline gateway access and require explicit confirmation. The product must not frame this as a harmless disable toggle.

R9 — deleteAccount may be re-enabled only after end-to-end proof

The suppression in extensions/clawline/src/channel.setup.ts may be removed only when the delete → re-add round-trip has product proof covering shutdown, config mutation, fresh-secret activation, and post-re-add CLU access.

R10 — Plain disable remains a separate, non-destructive action

openclaw channels remove clawline without delete semantics may continue to mean “disable but keep config,” but it must remain clearly distinct from destructive removal. T188 does not let a disable path substitute for safe delete proof.

Acceptance criteria

A1

A destructive remove request stops the live Clawline gateway before config deletion and reports failure if stop confirmation is missing.

A2

After destructive remove, the old cluSecret no longer grants CLU access and the gateway is not left listening in a stale-auth state.

A3

Re-adding Clawline writes a new non-empty server.cluSecret distinct from the prior deleted one.

A4

Post re-add, CLU requests with the new secret succeed and requests with the old secret fail.

A5

User-visible copy distinguishes disable vs delete and warns that delete stops Clawline gateway service.

A6

The implementation specifies exactly which config fields survive re-add, which are regenerated, and which must be re-entered or defaulted.

A7

deleteAccount is re-enabled only after the proof matrix in this spec is satisfied.

Open decisions / proposed answers

D1 — Secret reload mechanism

Proposed answer: require a controlled gateway restart for re-add v1. If later work proves a true in-process secret reload with equivalent safety, that can be a follow-up improvement. This keeps product truth aligned with T188’s stated failure mode instead of assuming current reload hooks solve auth skew.

D2 — Delete UX shape

Proposed answer: destructive delete should require explicit confirmation text that Clawline gateway access will stop and that re-adding will regenerate the CLU secret. Silent one-click delete is not acceptable.

D3 — Re-add posture

Proposed answer: treat re-add as guided re-onboarding that restores safe defaults and preserved non-secret fields where possible, rather than a minimal “just swap secret” hidden mutation. This better matches the fact that Clawline config is broader than a single credential.

Verification targets

V1 — Pre-delete live-state proof

Show Clawline gateway is running and CLU-authenticated requests work with the current secret before destructive remove.

V2 — Controlled stop proof

Show destructive remove causes a real gateway stop / listener-down result before config deletion is committed.

V3 — No-stale-auth proof

Show the old secret no longer authenticates once removal completes.

V4 — Fresh-secret proof

Show re-add writes a new secret distinct from the prior one.

V5 — Post-readd auth proof

Show the new secret authenticates CLU requests and the old secret is rejected after re-add.

V6 — User-facing UX proof

Show the delete confirmation warns about gateway stop and re-onboard impact, and that disable remains separately labeled.

V7 — Re-enable gate proof

Only after V1–V6 are satisfied may the deleteAccount: undefined suppression be removed.

Risks

K1 — Stale secret acceptance

If the old secret remains valid after re-add, CLU/gateway identity is ambiguous and the product is still broken.

K2 — Config deletion before stop

Deleting config first can strand a live gateway with no trustworthy on-disk source of truth and no safe way for CLU to reason about it.

K3 — Disable/delete UX confusion

If the destructive path looks like a harmless disable, users can break the whole Clawline control path accidentally.

K4 — Silent field loss

Re-add can damage product trust if user-owned non-secret settings disappear without warning or explicit defaulting rules.
