T343 Architecture Spec

Unified Keyboard Shortcut Routing

Prepared 2026-05-18. Source-of-truth architecture spec for one keyboard ownership model that survives transient input surfaces appearing and disappearing in Clawline.

Decision: Clawline will route all shortcut ownership through one central Keyboard Command Router backed by one router-owned Keyboard Ownership Store. Surfaces may expose capabilities and lifecycle, but they may not decide shortcut priority on their own, and platform bridges may not become a second truth source.

Problem

Keyboard behavior currently regresses when transient surfaces such as notification action menus, notification reply fields, and the composer mention picker appear or disappear. The failure mode is structural, not just one broken shortcut.

Invariant

Visible UI surfaces may register command intents, but only one router resolves ownership, priority, and dispatch for each keyboard event within the active chat scene.

Primary Seam

Platform capture normalizes keys into command intents. Surface handlers implement behavior. The router alone chooses which handler owns the event.

Hard Rule

No new raw shortcut policy may live in feature views such as notification overlays, rich text editors, or action menus after migration. Those surfaces register; they do not arbitrate.

Failure Topology

  • Shortcut policy has been patched into multiple surfaces instead of one routing layer.
  • Transient surfaces do not share one registration and teardown lifecycle, so stale ownership survives after UI disappears.
  • Focus is being used as a proxy for ownership even though explicit notification shortcuts are required to override text-field focus.
  • Platform-specific rescue code can capture keys before feature views see them, which creates a parallel truth risk if those bridges also choose targets.
  • Tests exist around individual symptoms, but the architecture has not made it hard to reintroduce the same class of bug in a new surface.

Non-Goals

  • This spec does not redefine transcript persistence, notification content rules, or mention-routing semantics already owned by T307.
  • This spec does not require a single store for all UI domain data. It requires a single source of truth for keyboard ownership state.
  • This spec does not forbid platform bridges. It forbids platform bridges from becoming an independent policy engine.
  • This spec does not add new user-facing shortcuts beyond the T307 and T342 product requirements.

Core Architecture

AR-01 Central Router Contract

The central router contract has three parts:

  1. A platform bridge turns raw keyboard events into normalized command intents.
  2. A router-owned registry knows which surfaces exist, which are active, and which command families they can legitimately handle.
  3. The router resolves one owner for each command intent and dispatches to that surface handler with an inspectable trace.
AR-02 Normalized Command Intents

Routing is done on semantic command intents, not direct view-level key matching. Example intent families include:

  • notification.assigned.open(number)
  • notification.assigned.reply(number)
  • notification.assigned.dismiss(number)
  • notification.scroll.forward and notification.scroll.backward
  • menu.navigate.up, menu.navigate.down, and menu.activate
  • picker.navigate.up, picker.navigate.down, and picker.accept
  • text.submit, text.newline.modified, and text.cancel
  • transcript.scroll and default fallthrough
AR-03 Surface Registration, Not Surface Arbitration

Each keyboard-capable surface registers a descriptor containing its kind, lifecycle token, scene, visibility, active state, focus hint status, and supported command families. A surface handler returns behavior for commands it owns, but it does not rank itself against sibling surfaces.

AR-04 One Owner Per Event

For any key event in the active chat scene, the router emits exactly one route decision: handled by one surface, explicitly ignored, or allowed to fall through. Two surfaces handling the same key event is an architecture bug.

AR-05 Inspectable Decision Trace

Every route decision must be inspectable in diagnostics. The trace should include the normalized intent, participating surfaces, the winning priority rule, and whether a platform bridge consumed the event before default platform handling.

Router-Owned State Model

The router is the only writer of routing-critical ownership state. Feature stores remain owners of domain data.

State Ownership Rules

SO-01 Router Owns Ownership

The router owns the authoritative answers to “which surfaces exist,” “which surfaces are active,” and “who owns this command.” No surface keeps a private authoritative copy of that state.

SO-02 Feature Stores Own Domain Payload

The composer owns draft text and mention query state. The notification store owns bubble order, visibility, reply draft content, reply-mode state, and action-menu content. The transcript store owns transcript data. The router references those stores by stable domain references and derived snapshots, but does not mirror their payload fields.

SO-03 Focus Is a Hint, Not the Policy Engine

Platform focus and first-responder state are inputs into routing, not the routing authority. This is required because T307 explicitly demands notification number shortcuts and notification scroll shortcuts that can override focused text inputs.

SO-04 Derived Shortcut Maps Must Stay Derived

Assigned notification numbers are derived from the notification store’s visible ordering and written only into router-owned derived state. No notification bubble may store a long-lived independent hotkey assignment that can drift after reorder or overflow changes.

SO-05 Scene-Scoped Ownership

Ownership is scoped to the active chat scene or window. A stale hidden scene must not continue to own shortcuts for a foreground scene.

SO-06 No Duplicate Convenience Truth

The router store must not keep second authoritative copies of active transient owner or focused owner outside the surface registry. Those are selectors derived from the registry, not parallel mutable fields.

SO-07 Shared Lifecycle Facts Have One Writer

Routing-relevant lifecycle facts such as “mention picker open,” “notification action menu open,” and “reply field active” must have one writer. Either the feature store owns the fact and drives router registration atomically, or the router lifecycle API owns it and the feature renders from that state. Both layers mutating the same fact is forbidden.

Lifecycle Rules

LC-01 Register on Mount or Appearance

Each keyboard-capable surface registers once when it enters the active chat scene. Registration returns an opaque lifecycle token that must be used for updates and teardown.

LC-02 Activate and Deactivate Without Reallocation

Transient surfaces such as mention pickers and action menus should usually toggle active and visible state on an existing registration rather than repeatedly re-creating ad hoc listeners. This keeps ownership changes explicit and inspectable.

LC-03 Unregister on Disappear or Domain Deletion

When a transient surface disappears, when its parent domain object disappears, or when the scene is torn down, the router must revoke its lifecycle token and remove its ownership claims immediately.

LC-04 Parent-Child Coupling for Transients

A mention picker is a child of the composer surface. A notification action menu and reply field are children of a notification bubble domain object. If the parent deactivates or disappears, child registrations are auto-revoked in the same route epoch.

LC-05 No Orphaned Global Capture

Platform bridges may stay installed for the scene, but they must consult the live router registry before consuming any command. A captured command with no current owner must fall through rather than resurrecting a stale surface.

LC-06 Navigation Resets Ownership Without Forcing Input Focus

Chat navigation must flush scene-local transient keyboard ownership and re-register the destination scene’s surfaces without opportunistically focusing the composer or a reply field. This preserves V307-25.

Priority Model

ID Priority Rule Owner Reason
PR-01 Open notification action menu owns menu arrows and Return/Enter. Notification action menu Menus are explicit transient interaction surfaces and must not leak navigation keys to the composer or transcript while open.
PR-02 Open composer mention picker owns picker arrows and mention-accept Return/Enter. Mention picker The picker is the active chooser for the composer and must intercept selection keys before text submit.
PR-03 Assigned notification number shortcuts always win while their target notification exists. Target notification bubble domain T307 makes these app-global notification commands, even over focused text fields.
PR-04 Visible-notification scroll shortcuts own Cmd-J/Cmd-K/Cmd-Shift-J/Cmd-Shift-K while visible notifications exist. Active or top notification bubble T307 explicitly requires these to remain available even when composer or reply fields are focused.
PR-05 Focused notification reply field owns plain text-entry keys, plain Return submit, modified Return newline, and Escape cancel. Notification reply field Reply editing is scoped text behavior after higher-priority notification-global commands are resolved.
PR-06 Focused composer owns normal text editing, plain Return submit, and modified Return newline. Composer The composer is the default active text surface when no stronger transient or notification-global rule applies.
PR-07 Transcript or default scene behavior receives only unclaimed commands. Transcript/default Fallback behavior must be explicit, not accidental leakage.

Important consequence: the router resolves notification-global commands before ordinary text focus, but it resolves plain text-entry keys after transient menu or picker ownership has had a chance to claim them.

Reference Routing Algorithm

route(intent, scene):
  candidates = registry.activeVisibleSurfaces(scene)

  if intent.family in menuNavigation and exists open notification action menu:
    return actionMenu

  if intent.family in pickerNavigation and exists open composer mention picker:
    return mentionPicker

  if intent.family in assignedNotificationCommands:
    return notificationShortcutMap[intent.number] or fallthrough

  if intent.family in notificationScroll and notificationsVisible(scene):
    return activeNotificationOrTopVisible(scene)

  if exists focused notification reply field and replyField.claims(intent):
    return replyField

  if exists focused composer and composer.claims(intent):
    return composer

  return transcriptOrDefault(scene)

Stale-Ownership Hardening

HO-01 No Raw Policy in Feature Views

Feature views may declare command capabilities and surface lifecycle only. They may not contain private priority decisions such as “if menu open then steal arrows before notifications.”

HO-02 Bridge Modules Are Capture Shims

Bridge files such as app-command shims, responder bridges, or DOM keydown capture may normalize events and ask the router what to do. They may not directly open reply mode, scroll a notification, move a picker selection, or navigate a menu.

HO-03 Auto-Revoke Child Surfaces

Mention pickers, action menus, and inline reply surfaces must be revoked by parent teardown. This prevents the exact stale transient-surface bug class that triggered T343.

HO-04 Derived Route Diagnostics

The app should expose a lightweight debug panel or log trace showing active surfaces, derived notification assignments, and last route decision. A stale owner becomes obvious instead of invisible.

HO-05 Review Gate for New Surfaces

Any future surface that can receive keyboard interaction must ship with a router registration descriptor, lifecycle tests, and explicit priority expectations. “I added a local key handler because it was easy” is a review failure.

HO-06 Registry Reconciliation Guard

The router must reconcile its registry against the live scene and parent domain objects on scene updates and before dispatch. If a parent surface or domain reference no longer exists, orphaned child registrations are pruned even if a view forgot to unregister cleanly.

Platform Bridge Rules

PB-01 Allowed Bridge Responsibility

A platform bridge may detect hardware-keyboard availability, normalize raw platform events, and capture commands that would otherwise be swallowed before declarative UI sees them.

PB-02 Forbidden Bridge Responsibility

A bridge may not choose between composer, reply field, mention picker, action menu, or transcript on its own. It must pass the normalized intent to the router and obey the router result.

PB-03 Platform Escape Hatch Still Routes Centrally

If Apple or web text controls require a responder-layer workaround for arrow keys, Return, or global command shortcuts, that workaround is still a bridge, not a policy branch. The same router decides ownership on every platform.

PB-04 One Intent Vocabulary Across Platforms

iOS/Catalyst, macOS, and web must normalize into the same command-intent vocabulary so precedence is defined once and tested once, even if capture details differ.

Migration Plan

MG-01 Create the Router and Intent Vocabulary

Introduce the central router contract, normalized command-intent types, surface registry, and route diagnostics before moving behavior. This is the new stable seam.

MG-02 Wrap Existing Text Surfaces

Register the composer and notification reply fields as router-backed text surfaces first. Preserve T342 modified Return newline semantics and plain Return submit within router-dispatched handlers.

MG-03 Move Mention Picker Ownership

Move picker arrow navigation and mention acceptance into a dedicated mention-picker surface registration. Remove view-local arrow and Return priority decisions once the router-backed picker passes.

MG-04 Move Notification Globals and Menus

Route assigned notification shortcuts, notification scroll shortcuts, and notification action-menu ownership through the router. The router derives notification shortcut assignments from the notification store’s visible ordering.

MG-05 Demote Platform Rescue Code

Refactor iOS/Catalyst app-command capture, responder overrides, and web keydown capture so those modules become thin bridge shims that only emit intents to the router.

MG-06 Delete Redundant Local Priority Logic

After router-backed behavior is in place, remove duplicated shortcut arbitration from current scattered paths recorded in the tracker, including iOS chat view logic, iOS rich text/editor capture, iOS notification app-command shims, and web notification overlay logic.

MG-07 Lock the Seam With Tests and Review Rules

Add precedence tests, lifecycle tests, and a review checklist that rejects new raw shortcut policy outside router or bridge modules. This is how future surfaces stop breaking ownership again.

Verification Gates

VG-01 Intent Normalization Tests

Unit-test iOS/Catalyst, macOS, and web bridge modules so the same physical shortcuts normalize into the same command intents.

VG-02 Precedence Matrix Tests

Table-driven tests must prove the router’s decisions for action menu, mention picker, notification globals, reply field, composer, and transcript fallback across conflicting states.

VG-03 Transient Lifecycle Tests

Explicitly test open, update, close, and parent-teardown transitions for mention pickers, notification action menus, and notification reply fields so stale ownership cannot survive disappearance.

VG-04 Regression Tests for T307 and T342

Carry forward focused tests for notification number shortcuts, notification scroll shortcuts, mention-picker navigation and acceptance, reply-field Return behavior, composer Return behavior, and modified Return newline behavior.

VG-05 Navigation and Focus Preservation Tests

Verify V307-25 explicitly: moving between chats or navigating from a notification must not summon the keyboard or shift ownership unless the user intentionally focused an input.

VG-06 Hardware Keyboard Proof

Run a physical or simulator-backed hardware-keyboard pass on Apple surfaces proving arrow, Return, modified Return, and global notification shortcuts on the actual UI layer, not just compile-time assumptions.

VG-07 Architecture Review Gate

Review must include a requirement matrix against this spec and reject any remaining surface-local shortcut priority logic or parallel bridge-owned ownership decisions as unsatisfied architecture requirements.

Embedded Adversarial Review Verdict

Verdict: Pass after revision. The first draft risked letting focus or platform fallback remain de facto authority. The revised architecture closes that hole by making the router-owned registry and normalized command-intent pipeline the only ownership truth.

RV-01 Blocker Fixed: Focus Was Not Reliable Truth

The spec now states that focus is only a hint, because T307 requires notification-global shortcuts to override focused text fields. Ownership now lives in router state, not responder state.

RV-02 Blocker Fixed: Platform Bridges Could Have Become Parallel Policy

The bridge rules now explicitly forbid bridges from choosing targets or mutating feature state directly. Bridges capture and normalize only; the router decides.

RV-03 Blocker Fixed: Transient Surfaces Needed Stronger Teardown

The lifecycle rules now require parent-child auto-revocation and scene teardown cleanup, which directly attacks the stale ownership bug class behind the mention-picker regression.

RV-04 Blocker Fixed: Duplicate Hotkey Assignment Drift

The spec now makes assigned notification numbers derived router state rather than bubble-owned persistent state, which closes a future reorder or overflow drift footgun.

RV-05 Blocker Fixed: Shared Open-State Split Brain

The spec now requires a single writer for routing-relevant lifecycle facts such as picker open state, action-menu open state, and reply activation. That closes a quiet duplicate-state seam that could otherwise recreate stale ownership even with a central router.

RN-01 Residual Risk: Implementation Discipline

A future contributor can still add a raw keyboardShortcut, onKeyDown, responder override, or bridge-side mutation if review discipline slips. VG-07 and HO-05 are therefore part of the architecture, not optional cleanup.

RN-02 Residual Risk: Cross-Store Atomicity

The router depends on up-to-date notification visibility ordering from the notification store. Implementation should wire that dependency atomically so shortcut reassignment cannot lag one frame behind visible stack changes.
